# MV3 陈旧 bundle 陷阱 —— 扩展更新后功能"没修复"

## 症状（多次出现）
- 修复了某 bug 并发布，用户反馈"还是不行"——日志显示**旧代码在运行**
- 实例：未分类跳转 `?? "__unclassified__"` 已修但进入全部卡片视图；公式捕获失效；悬停感知与 Alt+S 行为不一致

## 根因
Chrome MV3 的**内容脚本只在页面加载时注入** + **options 扩展页不随扩展更新自动刷新**：
1. 扩展更新 → **已打开的网页仍运行旧内容脚本 bundle**（不会被重新注入）
2. **已打开的 options 页**（`options.html`）仍运行旧 bundle（直到手动重开）

所以"代码已修 + 构建通过 + 测试绿"≠"用户看到的修复"——用户在跑旧 bundle。

## 排查
- 贴出的日志 `options.95eda3f3.js:245` ——该哈希是**入口级哈希，内容变化不改变** → 不能证明 bundle 新旧
- 用临时 `console.warn` 日志确认实际执行的是哪份代码

## 修复
- 无代码修复——**重载扩展 + 刷新测试页 / 重开 options 页**后功能即正常
- 排查方法论：功能"没修复"时先确认 bundle 是否刷新，再做代码级根因分析

## 通用教训
- MV3 内容脚本 + 扩展页的刷新机制决定了：**验证必须用全新会话**（重载扩展 + 刷新页面）
- bundle 哈希（entry-level）不能证明新旧——用运行时日志或行为验证
- "功能完全失效"先查框架边界（注入/刷新），memory #124 的完整链路追踪原则
